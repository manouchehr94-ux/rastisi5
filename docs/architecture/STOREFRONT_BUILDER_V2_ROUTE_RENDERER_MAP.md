# Storefront Builder V2 — Route / Renderer Map

**Phase:** Audit checkpoint. Documentation only.

> **Pointer note (added during the subsequent architecture-revision pass):** the route/template/shell findings below are unchanged factual observations and are not re-litigated here. The owner has since locked the target multi-page domain model (`StorefrontLayoutVersion → StorefrontPage → StorefrontSection`, see `STOREFRONT_BUILDER_V2_IMPLEMENTATION_PLAN.md` §1) that Phase 1 will use to make every route below Section/Block-composable. The "V2 migration requirement" column below still accurately describes what each route needs; it should now be read as "needs a `StorefrontPage` of the corresponding `page_type`" rather than an open/undecided shape.

All evidence below is `SOURCE_ONLY` (templates, views, and urls.py read directly; no request was executed against a running server — no Django runtime is available in this sandbox, see `STOREFRONT_BUILDER_V2_EXISTING_CAPABILITY_AUDIT.md` §0).

Tenant resolution for **every** route below is `apps.stores.resolution.resolve_store_for_storefront(request)` — the single authoritative "which Store" resolver, fail-closed (404 for unresolvable/ineligible host, 403 for a real-but-not-publicly-visible Store).

## Definitive answer to the browser-QA question

**Source-level root cause of "the homepage and collection/listing pages can visually behave like different storefronts":**

Exactly **two** templates in the entire repository include the shared, Family-aware page shell partials (`page_shell_header.html`/`page_shell_footer.html`): `catalog/home_visual.html` (the public homepage, only once a Builder layout has been published) and `storefront_builder/preview.html` (the staff-only Draft preview). **Every other public template** — the legacy homepage fallback, Product Detail, Product Listing, Category-filtered listing, Collection Index/Detail, Search, Cart, Wishlist, and Content Pages — extends `templates/base.html` directly and renders `base.html`'s own hardcoded `{% block header %}` / `{% block footer %}` verbatim, with **zero** overriding block definitions in any of those child templates (confirmed by direct inspection of each template's `{% extends %}`/`{% block %}` structure).

The only two things that *do* reach every route regardless of Family selection are:
1. **Global appearance tokens** (colors, fonts, radius, motion) — applied everywhere via the always-active `shop_settings` context processor, correctly universal.
2. **The product card partial** (`catalog/partials/product_card.html`) — Family-aware, and included on Home, Product Listing, and (architecturally) Collection pages, so product cards look consistent with the merchant's chosen Family even on otherwise-generic pages, while the surrounding page chrome does not.

This is not a rendering bug or a template-resolution defect — it is the direct, structural consequence of only two templates having ever been wired to include the shared shell partials. It is the single most concrete, evidence-based justification for the V2 spec's core principle: *"every public storefront page must be rendered through the same storefront design system"* (spec §2) is **not yet true today**, and fixing exactly this gap (wiring every route's shell through one common include, the way `home_visual.html`/`preview.html` already do) is very likely the cheapest, highest-leverage first step of any V2 Phase 1 — see the Implementation Plan document.
